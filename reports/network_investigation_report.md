# Network Investigation Report

## Enterprise Phishing Incident Response Center

### Investigation Objective

The purpose of this investigation was to demonstrate network-level analysis as part of the phishing incident response workflow. Wireshark was used to capture and inspect network traffic, with emphasis on DNS activity that could assist an analyst in identifying domains contacted by an endpoint during an investigation.

---

## Evidence Source

- Tool: Wireshark
- Capture Interface: Wi-Fi
- Evidence File: `05_phishing_network_investigation.pcapng`
- Analysis Focus: DNS traffic and domain-resolution activity
- Display Filter: `dns`

---

## Investigation Procedure

1. Captured live network traffic from the Windows endpoint using Wireshark.
2. Applied the `dns` display filter to isolate DNS queries and responses.
3. Reviewed source and destination IP addresses associated with DNS activity.
4. Examined queried domain names and corresponding DNS responses.
5. Preserved the packet capture as `05_phishing_network_investigation.pcapng` for investigation evidence.

---

## Observed Network Activity

The packet capture contained DNS queries generated by the endpoint and responses from the configured DNS resolver.

Examples observed during the capture included domains associated with legitimate services such as:

- `api.grammarly.com`
- `win-extension.femetrics.grammarly.io`
- `inkwell.femetrics.grammarly.io`
- `login.microsoftonline.com`
- `catalog.gamepass.com`
- `skydrive.wns.windows.com`

The workstation was observed communicating with the local DNS resolver using UDP destination port 53.

---

## Analyst Assessment

The captured DNS traffic demonstrates the network-analysis stage of a phishing investigation. DNS evidence can help a SOC analyst identify domains contacted by an affected endpoint and correlate those domains with indicators extracted from suspicious emails, URLs, attachments, threat-intelligence sources, and SIEM events.

The domains observed in this lab capture are not classified as malicious based solely on this packet capture. The capture is therefore used as a controlled demonstration of the investigative methodology rather than evidence that these legitimate services were involved in the simulated phishing incident.

---

## Threat Intelligence Correlation

The phishing investigation workflow also includes file-hash enrichment through VirusTotal.

The test attachment hash was submitted for lookup, and the API returned HTTP 404 because the generated lab hash was not present in VirusTotal's existing dataset.

This result was retained as part of the investigation because an unknown hash does not automatically indicate that a file is safe or malicious. Additional evidence and analyst review are required.

## SOC Investigation Workflow

Suspicious Email
→ Email/IOC Extraction
→ Attachment Hashing
→ Risk Scoring
→ Threat Intelligence Lookup
→ Splunk SIEM Analysis
→ Network Investigation
→ Analyst Decision
→ Escalation / Incident Response

---

## Recommended Analyst Actions

For a suspected phishing incident, the analyst should:

1. Correlate DNS domains with URLs extracted from the suspicious email.
2. Review endpoint activity surrounding the phishing event.
3. Enrich domains, URLs, IP addresses, and hashes using approved threat-intelligence sources.
4. Search Splunk for related activity across other endpoints and users.
5. Determine whether credentials were entered or suspicious content was executed.
6. Escalate high-risk incidents according to the incident-response playbook.
7. Preserve relevant email, SIEM, threat-intelligence, and packet-capture evidence.

---

## Conclusion

This investigation demonstrates how network packet analysis can complement email analysis, automated phishing risk scoring, threat-intelligence enrichment, and Splunk-based SOC monitoring.

The Enterprise Phishing Incident Response Center combines multiple investigation stages to provide an evidence-driven workflow for phishing detection, triage, investigation, escalation, and response.
